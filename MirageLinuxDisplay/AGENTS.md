# AGENTS.md（C/C++ 混合项目）

## 禁止探测与兜底

- 禁止通过运行时探测、强转、字符串清洗、normalize 或兜底逻辑兼容输入。
- 默认前提：项目内字段名、类型、协议、缓冲区结构、内存所有权均可从上下文、文档、头文件、struct/class 定义、接口原型、IDL/协议表、字段表中确认，不得擅自视为未知输入。
- 在未完成上下文检索前，禁止：
  - 将字段/缓冲区视为 mixed 类型；
  - 添加兼容性分支；
  - 添加 normalize/extract/payload 类函数；
  - 添加字符串/内存清洗逻辑。
- 在可能未知类型的情况下禁止生成或保留以下模式，而是向用户询问或根据上下文判断实际结构：
  - `dynamic_cast` + `nullptr` 兜底分支
  - `typeid` / `std::any` / `std::variant` 运行时类型探测
  - `reinterpret_cast` / C 风格 `(T)x` 强转
  - `void*` / `uintptr_t` 携带业务数据 + 运行时 tag 探测
  - `union` 类型双关读写不同类型
  - `#ifdef` / `#if defined` 兼容性分支（有明确依据的语言边界守卫如 `__cplusplus` 除外）
  - `if constexpr` / SFINAE / concepts 编译期特性探测分支
  - `strlen` / `strnlen` / `memchr` 探测结尾或长度
  - `atoi` / `atof` / `strtol` / `sscanf` 静默容错转换
  - 手写 `isspace` trim / `tolower` / `toupper` 清洗
  - `= -1` / `= nullptr` / `= {}` / `= 0` fallback default
  - `try` / `catch(...)` / 空 catch 吞异常
  - `(void)ret;` 式丢弃返回值、忽略 `errno`
  - 对非 trivial 类型或未确认长度执行 `memset` / `memcpy`
  - `alloca` / VLA 变长数组
  - weak symbol / `dlsym` / `GetProcAddress` 运行时探测
  - `normalize\*` / `extract\*` / `payload\*` / `parse\*_safe` 类命名
- 对于已知 enum、struct、class、DTO、协议字段：错误必须按项目约定自然抛出异常或返回错误码，不允许探测、纠正、修复或兼容。
- 如果字段、结构、协议无法从上下文或文档明确确认：禁止猜测实现；禁止添加兜底；必须直接拒绝修改，并列出缺失的类型信息或协议定义。
- 当继续实现所需的字段、类型、协议或结构信息缺失时：禁止探测、推断、兼容或兜底实现；必须立即停止修改，并输出明确错误，说明缺失的具体信息及无法继续的原因。

## C/C++ 混合边界

- C 与 C++ 共享的头文件必须同时满足：
  - 使用 `#ifdef __cplusplus extern "C"` 守卫包裹对外声明；
  - 只含 C 兼容声明：无类、模板、命名空间、引用、默认参数、函数重载；
  - 使用 `uint32_t` / `int64_t` 等定宽类型，边界上禁止暴露 `int` / `long` / `size_t` 等宽度含糊类型（项目约定除外）；
  - 禁止暴露 `bool`，统一使用 `uint8_t` 或项目定义类型；
  - 结构体布局与对齐必须显式声明（按项目约定使用 `#pragma pack` / `_Alignas`），禁止依赖编译器默认打包。
- `.c` 文件只写 C，`.cpp` / `.cc` / `.cxx` 文件只写 C++；禁止通过构建脚本切换语言模式让 C 代码依赖 C++ 特性，反之亦然。
- 跨语言调用一律经过边界头文件；禁止 C 层直接引用 C++ 内部符号，禁止 C++ 层直接操作 C 内部 static / 全局变量。
- 内存所有权必须在注释中写明“谁分配、谁释放”；禁止 `new` 配 `free`、`malloc` 配 `delete/delete[]` 混用；跨边界对象一律使用归属方提供的创建/销毁函数对。
- 跨边界字符串/缓冲区一律使用“指针 + 长度”，或在接口中明确约定 `'\0'` 结尾；禁止运行时猜测结尾或长度。

## 错误处理与返回值

- C 层统一使用错误码（或项目现有约定），错误码必须为枚举，禁止魔法数字；C++ 层异常/返回码风格跟随所在模块现有约定，禁止同一模块内混用两种风格。
- 任何函数调用的返回值必须被显式处理；确可忽略时必须在注释中说明原因。
- 资源获取（内存、fd、锁、handle）与投递（队列、线程池、异步任务）失败必须有明确处理；禁止不检查返回值，禁止基于“假设成功”的补偿分支。
- 报错风格遵循接口约定：约定抛异常的接口不得再靠检查返回值判错；约定返回错误码的接口不得用 try/catch 吞掉或忽略返回值。

## 最小实现原则

- 默认在现有类和现有方法内完成需求，允许少量局部重复，并保持最小修改范围。
- 代码相似、调用次数相当前实现相同都不能单独证明抽象必要；“存在至少两处调用”只能作为评估信号，不能作为允许新增抽象的充分条件。
- 共享抽象的所有调用方必须同时满足以下条件：
  - 属于同一个明确的业务概念；
  - 遵循同一个协议和业务约束；
  - 预期因同一个业务原因共同变化。
- 上述任一条件不满足时，禁止共享抽象：即使存在两处或更多相同代码，也必须分别保留局部实现。
- 实现前必须检查当前项目是否存在职责相同的抽象：
  - 新逻辑与现有抽象的业务概念、协议、业务约束和变化原因均一致时，必须直接复用或扩展现有抽象，禁止新增平行抽象；
  - 仅实现形态相似但业务独立时，禁止复用现有抽象，也禁止为了消除重复而创建新的共享抽象；
  - 禁止通过轻微改名、参数差异、继承、组合或包装旧抽象调用创建职责重叠的新抽象。
- 新增文件、头文件、类、命名空间、模板、宏、struct、DTO、Helper、Hook、Service、组件或函数，必须同时满足以下全部条件：
  - 当前需求已经存在多处真实调用；
  - 所有调用方属于同一业务概念并因同一业务原因共同变化；
  - 局部实现会产生具有相同业务含义的非简单重复，或产生无法通过局部调整解决的复杂分支；
  - 当前项目不存在职责相同且可以直接复用或扩展的实现。
- 仅被调用一次、仅包装现有调用、仅转发参数或仅返回调用结果的抽象禁止新增。
- 不得仅因为方法较长、代码可以命名、便于测试或可能复用而提取新方法；必须先通过局部变量、直接条件判断或整理现有方法完成需求。
- 禁止以“以后可能用”、“便于扩展”、或设计模式完整性为理由预设结构。
- 无法确认调用方是否属于同一业务概念、遵循同一协议或共同变化时，默认不抽象，并向用户列出缺失的信息。
- 完成修改后必须逐一检查每个新增文件、类和方法：无法直接证明必要性的抽象必须删除。

## 函数签名与类型

- 新增任意 function / method 时，必须显式声明全部参数类型和返回值类型；禁止 `auto` 参数、禁止外部接口使用推导返回类型；模板/泛型仅在项目已有约定或需求明确要求时使用，否则先询问。本规则强调“新增”，不要求顺手改动既有未声明签名，除非本次修改确实触碰该函数签名。
- C 函数必须在头文件中给出完整原型，禁止 K&R 风格定义、隐式声明、缺省 `int`。
- 禁止用 `void*` + 类型标记模拟泛型接口；禁止用宏模拟重载（项目已有明确约定的除外）。
- 指针参数必须明确可空性与所有权；只读指针与只读参数必须加 `const`。
- 协议/边界字段一律定宽类型；`size_t` 仅用于长度与大小，并遵循项目约定。

## 注释属于强制要求

- 所有新增或修改的代码必须包含必要注释。
- 注释必须说明：
  - 此实现解决什么问题；
  - 为什么必须这样实现；
  - 为什么选择当前方案而不是其它方案；
  - 存在的约束、协议要求、边界条件、内存所有权、线程安全假设或历史兼容原因。
- 头文件对外接口必须额外说明：参数所有权与可空性、缓冲区长度要求、字符串结尾约定、线程安全性、错误返回/异常行为。
- 禁止无意义注释，包括但不限于：
  - 重复代码字面含义；
  - “设置变量”“循环数组”之类的描述；
  - 与代码行为不一致的注释。
- 注释必须与实现保持同步；修改逻辑时必须同步更新注释。

## 编译与构建

- 新代码必须在项目现有警告等级下零警告通过编译；禁止无注释说明理由的 `#pragma` 抑制警告或强转消警。
- C 按项目约定标准（如 C11/C17）、C++ 按项目约定标准（如 C++17）编写，禁止使用超出约定标准的特性；禁止擅自修改构建配置升级标准或切换语言模式。
- 禁止擅自引入新的第三方依赖；禁止擅自新增编译选项、链接库（除非需求明确要求并经用户确认）。
- 只 include 必要头文件；能前向声明降低依赖的优先前向声明。
